# Часть 4. Метрики и журналы

## 10. Что даёт мониторинг

Число «CPU 95%» отвечает на вопрос о нагрузке, но не объясняет, какой запрос вызвал проблему. Строка access.log показывает конкретный запрос, но не показывает запас памяти всей машины. Поэтому метрики и журналы дополняют друг друга.

Zabbix agent установлен на каждой ВМ. Сервер обращается к нему по TCP 10050, используя внутренний DNS. Ответ содержит значение конкретного item: загрузку CPU, использование памяти или пользовательский счётчик. В конфигурации также указан адрес активных проверок, но основные items этого проекта собираются в пассивном режиме. Не говорите, что все метрики «отправляются агентом самостоятельно»: направление зависит от типа item.

| Термин Zabbix | Смысл | Пример |
|---|---|---|
| Host | Наблюдаемый узел | diplom-web-a |
| Item | Одно измерение | Процент использования диска |
| History | Отдельные измерения | Значения каждые 30 секунд |
| Trend | Агрегат истории | Среднее, минимум, максимум за час |
| Trigger | Условие проблемы | Диск больше 80% |
| Graph | График значений | CPU и пороговая линия |
| Dashboard | Набор визуализаций | USE по всем шести ВМ |

> **Ключевая мысль.** Зелёная страница входа в Zabbix не доказывает мониторинг. Доказательство — поддерживаемые items с обновляющимися lastvalue, история и работающие проверки.

### Вопросы на защите

**Почему Zabbix server в контейнере, а агент в ОС?** Серверу нужны БД и веб-интерфейс; контейнеры упрощают установку. Агент в ОС читает ресурсы самой ВМ без путаницы с ограничениями контейнера.

**Зачем PostgreSQL?** Zabbix хранит там конфигурацию, историю измерений, события и пользователей. Потеря БД — потеря этих данных даже при работающем веб-контейнере.

**Где посмотреть ошибки агента?** `journalctl -u zabbix-agent` и `/var/log/zabbix/zabbix_agentd.log`.

## 11. USE на реальных ресурсах

USE расшифровывается как Utilization, Saturation, Errors: занятость ресурса, наличие очереди или давления и ошибки. Один высокий процент загрузки не всегда проблема. Если CPU занят полезной работой и очередь не растёт, машина может быть эффективно загружена. Если средняя загрузка по CPU невысока, но I/O очередь растёт, причина может быть в диске.

| Ресурс | Utilization | Saturation | Errors |
|---|---|---|---|
| CPU | 100 минус idle | Load average на ядро | Аппаратные ошибки ядра, отдельно от нагрузки |
| RAM | Использованная память % | Swap %, allocation stalls | Ошибки выделения и сигналы давления требуют дополнительной диагностики |
| Диск | Использование корневой ФС % | Незавершённые I/O в /proc/diskstats | I/O errors в журнале ядра |
| Сеть | Входящие/исходящие байты в секунду | Dropped packets | RX/TX errors |
| HTTP | Запросы и соединения | Активные соединения, длительность ответа | 5xx и неуспешный HTTP-сценарий |

Виртуальная машина не всегда предоставляет аппаратные счётчики физического CPU. Поэтому в книге нельзя обещать диагностику физического процессора по одной гостевой метрике. Нулевой счётчик kernel hardware errors означает «в доступном журнале таких сообщений не обнаружено», а не «железо гарантированно идеально».

Счётчики байтов и запросов накапливаются со временем. Чтобы получить скорость, Zabbix должен вычислить разницу между соседними измерениями и разделить её на время: preprocessing «Change per second». Без этого график с названием «байт/сек» на самом деле показывает сумму всех байтов с момента запуска — типичная ошибка начинающего администратора.

Пороговые линии не универсальны. CPU 80%, память 90%, диск 80% — учебные стартовые значения. Для CPU и RAM триггер использует усреднение за пять минут, чтобы одиночный всплеск не создавал лишний инцидент. При росте числа запросов пороги пересматривают с учётом запаса ёмкости.

```bash
cat /proc/loadavg
free -h
df -h /
cat /proc/net/dev
systemctl --failed --no-pager
sudo -u zabbix /usr/local/bin/diplom-metrics disk.queue
```

`free -h` показывает память в удобных единицах. Обращайте внимание на available: Linux использует свободную память для полезного кэша, поэтому маленькое free не всегда означает нехватку RAM. `df -h /` показывает заполнение файловой системы, а не нагрузку диска. Последняя команда запускает тот же коллектор от того же пользователя, что и агент. Это позволяет поймать проблему прав, которую запуск от root скрывает.

### Вопросы на защите

**Почему CPU 100% не обязательно авария?** Важны очередь, длительность нагрузки и пользовательские симптомы.

**Чем заполнение диска отличается от I/O queue?** Первое показывает занятое место; второе — ожидающие или выполняющиеся операции ввода-вывода.

**Почему появился unsupported item?** Возможны неподдерживаемый ключ, отсутствие разрешений, неверный интерфейс или ошибка пользовательского скрипта. Проверяйте поле error и запускайте коллектор от пользователя zabbix.

## 12. Путь журналов

nginx записывает access.log и error.log. Filebeat читает их, хранит позицию чтения в своём registry и отправляет события в Elasticsearch по 9200. Elasticsearch индексирует документы. Kibana обращается к Elasticsearch и показывает их человеку. Kibana сама не является хранилищем журналов.

Docker volume Filebeat сохраняет registry после перезапуска контейнера. Без этого агент может повторно прочитать старые события. Volume Elasticsearch сохраняет индексы; удаление контейнера при сохранённом volume не должно удалять документы. Удаление volume — уже уничтожение данных.

```bash
sudo tail -n 10 /var/log/nginx/access.log
sudo tail -n 10 /var/log/nginx/error.log
sudo docker ps
sudo docker exec filebeat filebeat test output --strict.perms=false
curl -s http://diplom-elastic.ru-central1.internal:9200/_cluster/health
curl -s 'http://diplom-elastic.ru-central1.internal:9200/nginx-*/_count'
```

Команды `curl` к Elasticsearch выполняются внутри VPC. Внешнему посетителю порт 9200 не доступен. `test output` подтверждает соединение и совместимость с сервером, но не гарантирует успешную индексацию каждого события. Для этого проверяйте количество документов и журналы Filebeat.

Во время настройки возникла реальная ошибка схемы: поле `service` было строкой `nginx`, а стандарт ECS ожидает объект, например `service.name`. Elasticsearch возвращал 400 и отвергал события, хотя TCP-соединение работало. Исправление — передать `service: {name: nginx}`. Этот случай показывает, почему проверки «процесс запущен» недостаточно.

### Вопросы на защите

**Что такое индекс?** Логическая группа документов с настройками поиска и схемой полей.

**Что такое data view в Kibana?** Представление, описывающее, какие индексы читать и какое поле использовать для времени.

**Почему health Elasticsearch бывает yellow?** В single-node схеме реплика shard не может размещаться на том же узле, что primary. Primary доступен, но реплика не назначена. Для учебного индекса replicas можно поставить 0; это не создаёт отказоустойчивость.

## 13. Чтение ошибки по слоям

| Симптом | Первый шаг | Следующий шаг |
|---|---|---|
| В Kibana нет событий | Проверить временной диапазон и data view | Проверить count индекса |
| Count равен нулю | Убедиться, что nginx пишет журнал | Проверить Filebeat и mapping ошибки |
| Elasticsearch недоступен | Проверить контейнер и порт | Проверить SG, DNS, RAM |
| Zabbix не получает данные | Проверить item error | Проверить доступ к агенту и ключ |
| Дашборд пуст после создания | Дождаться нескольких интервалов | Проверить history и supported items |

### Вопросы на защите

**В чём разница метрики и лога?** Метрика — измерение состояния или счётчика; лог — запись конкретного события.

**Почему журнал ошибок может быть пуст?** Если nginx не встретил ошибок, это нормально. Для проверки пути создайте контролируемый запрос к отсутствующему файлу и подтвердите запись без имитации журнала вручную.

**Что делать при Kibana 502?** Проверить состояние Kibana и её соединение с Elasticsearch; nginx reverse proxy может работать, пока upstream ещё запускается.
