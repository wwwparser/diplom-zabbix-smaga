Часть 1. Архитектура и сети

1. Что вообще требуется построить

Представьте небольшой информационный сайт. Его содержимое — HTML-файл, который браузер получает по сети. Если единственная машина сломается, пользователь увидит ошибку. Поэтому в дипломе два одинаковых веб-сервера. Перед ними находится балансировщик: он выбирает, куда отправить очередной запрос, и проверяет работоспособность каждого сервера.

Но доступность — только одна обязанность администратора. Нужно заметить заполнение диска, найти причину ошибок и восстановить данные после потери машины. Поэтому вокруг сайта построены три системы: Zabbix для числовых метрик, Elasticsearch с Kibana для журналов и расписание снимков дисков для восстановления.

Узел Роль Почему отдельная машина
diplom-web-a nginx, первая копия сайта Первый домен отказа
diplom-web-b nginx, вторая копия сайта Другая зона доступности
diplom-zabbix Сервер мониторинга, БД и интерфейс Наблюдает за остальными
diplom-elastic Хранилище журналов Изолировано от интернета
diplom-kibana Поиск и визуализация журналов Веб-интерфейс для оператора
diplom-bastion SSH и запуск Ansible Единственная точка административного входа

Ключевая мысль. Отказоустойчивость сайта и отказоустойчивость всех вспомогательных сервисов — разные задачи. В этом стенде сайт имеет две копии, Elasticsearch и Zabbix имеют по одному узлу.

Вопросы на защите

Почему не разместить всё на одной ВМ? Общий отказ выключит одновременно сайт, мониторинг и журналы. Кроме того, диплом прямо требует отдельные машины для этих ролей.

Что означает «зона доступности»? Это отдельная инфраструктурная площадка облака. Размещение копий в разных зонах снижает зависимость от одной площадки, но не защищает от общей ошибки конфигурации обеих копий.

Почему сайт статический? Его легко синхронизировать: одинаковые файлы можно отправить на оба сервера. Приложению с пользовательскими загрузками потребовалось бы отдельное общее хранилище.

2. Частные и публичные IP-адреса

IP-адрес — числовой адрес сетевого интерфейса. Внутри стенда используются адреса 10.42.*.*, которые относятся к частному диапазону. Интернет не маршрутизирует к ним пакеты напрямую. Публичный адрес выдаётся только тем узлам, с которыми должен общаться внешний пользователь или администратор.

VPC — логическая сеть проекта. Подсеть — её участок с собственным диапазоном адресов и привязкой к зоне. В Terraform созданы четыре подсети: публичные в зонах a и b, приватные в тех же зонах. Веб-серверы находятся в приватных подсетях; наличие слов «public» и «private» в имени не создаёт защиты автоматически. Защита возникает из сочетания отсутствия внешнего адреса, маршрутов и правил security groups.

DNS позволяет заменить числовой адрес именем. diplom-web-a.ru-central1.internal — внутреннее полное имя, или FQDN. Оно разрешается внутри облачной сети. На домашнем компьютере такое имя обычно не работает: домашний DNS не знает внутреннюю зону облака. Поэтому Ansible запускается на бастионе, который находится внутри VPC.

hostname
hostname -f
ip -br address
ip route
getent hosts diplom-web-a.ru-central1.internal

hostname показывает короткое имя машины. -f просит полное имя. ip -br address сокращённо выводит интерфейсы и адреса. ip route показывает маршруты: строка default via ... означает шлюз для неизвестных направлений. getent hosts проверяет разрешение имени тем же системным механизмом, которым пользуются обычные приложения. Если команда не вернула адрес, SSH по имени тоже не заработает.

Вопросы на защите

Почему inventory содержит имена, а не IP? Это требование диплома и способ отвязать автоматизацию от назначенного числового адреса. Но имя должно разрешаться там, где запускается Ansible.

Достаточно ли убрать внешний IP? Для закрытия прямого входа из интернета — важный шаг, но внутренние соединения всё равно надо ограничивать security groups.

Может ли приватная ВМ обновить пакеты? Да, если у неё настроен исходящий маршрут через NAT.

3. NAT, бастион и security groups

NAT-шлюз нужен приватным ВМ для исходящих соединений: скачать пакет Ubuntu, Docker-образ или обновление Filebeat. Он подменяет частный адрес источника внешним. Ответ возвращается по уже созданному соединению. Это не делает ВМ доступной для произвольного входа из интернета.

Бастион решает другую задачу. Администратор соединяется с ним по SSH, затем обращается к внутренним машинам. На бастионе нет публичного веб-приложения. Здесь запускается Ansible. Для автоматизации создаётся отдельный ключ: закрытая часть остаётся на бастионе, открытая добавляется на управляемые машины.

Security group — набор разрешённых соединений на виртуальном сетевом интерфейсе. В стенде SSH к внутренним узлам разрешён с адреса бастиона; Zabbix agent принимает запросы с сервера мониторинга; Elasticsearch принимает HTTP только из внутренней сети. Публичный балансировщик принимает HTTP на 80. Kibana принимает соединения на 5601 через nginx с аутентификацией.

ssh ubuntu@PUBLIC_BASTION_IP
ssh ubuntu@diplom-web-a.ru-central1.internal
sudo ss -lntp

Первая команда выполняется на компьютере администратора. Вторая — на бастионе. ss -lntp показывает слушающие TCP-сокеты: -l только слушающие, -n без преобразования номеров в имена, -t TCP, -p процессы. sudo требуется для просмотра всех процессов.

При недоступности SSH сначала проверьте маршрут и правила, затем наличие слушающего процесса и только потом ключ. Таймаут соединения и Permission denied (publickey) — разные ошибки: при второй сервер уже ответил, значит проблема не в маршруте.

Вопросы на защите

Чем NAT отличается от бастиона? NAT обеспечивает исходящий сетевой доступ; бастион обеспечивает контролируемый административный вход.

Почему нельзя держать SSH открытым всему интернету? Это увеличивает поверхность атаки. Ключи важны, но сетевое ограничение добавляет отдельный защитный слой.

Как подключались при проблемах домашнего маршрута? Через существующий сервер-посредник, который передавал SSH-трафик. Он не запускал сервисы диплома и не заменял ВМ Яндекс Облака.

Проверь себя

  1. Какой сервис первым принимает HTTP-запрос? 2. Почему web-b в другой зоне? 3. Зачем Elasticsearch скрыт от интернета? 4. Что такое FQDN? 5. Где выполняется Ansible? 6. Зачем NAT? 7. Что показывает ip route? 8. Чем таймаут отличается от отказа ключа? 9. Кто обращается к порту 10050? 10. Зачем отдельный ключ автоматизации?
Ответы 1. Application Load Balancer. 2. Чтобы не зависеть от одной зоны. 3. В нём хранятся журналы; прямой публичный доступ не нужен. 4. Полное доменное имя. 5. На бастионе. 6. Для исходящих соединений приватных ВМ. 7. Таблицу маршрутов. 8. Таймаут обычно предшествует SSH-аутентификации; отказ ключа означает, что сервер достигнут. 9. Zabbix server. 10. Чтобы не размещать личный долговременный ключ на сервере. Менее 7 правильных ответов — вернитесь к схеме и пройдите путь HTTP и SSH вслух.

Часть 2. Terraform и Ansible

4. Зачем инфраструктура описана кодом

Можно создать шесть ВМ вручную в консоли, но тогда результат зависит от памяти администратора. В одной машине забудут группу безопасности, во второй окажется другая зона, в третьей — неправильный диск. Terraform хранит желаемую структуру в файлах .tf. Он обращается к API облака и создаёт ресурсы по этому описанию.

Terraform не устанавливает nginx внутри Ubuntu. Его область ответственности — сеть, ВМ, диски, балансировщик и расписание снимков. Ansible подключается к уже созданным машинам по SSH и настраивает ОС и приложения. Разделение помогает диагностировать ошибки: если ВМ не создана, проверяйте Terraform; если nginx не запущен на существующей ВМ, проверяйте Ansible и журнал службы.

Файл Назначение
terraform/main.tf Все ресурсы Яндекс Облака
.terraform.lock.hcl Зафиксированный провайдер
.private/vars.json Значения облака, каталога и ключа оператора
terraform.tfstate Связь кода с реальными ресурсами, не публикуется
ansible/inventory.ini FQDN управляемых ВМ и группы
ansible/site.yml Порядок настройки сервисов
ansible/secrets.yml Пароли, исключены из Git

Ключевая мысль. Код описывает намерение, state описывает уже известное Terraform состояние. Потерять state — не то же самое, что удалить ВМ: ВМ останутся, но автоматизация перестанет знать, какими объектами она управляет.

Вопросы на защите

Почему не только Ansible? Ansible тоже умеет работать с облачными API, но в этом проекте Terraform отвечает за зависимости и жизненный цикл облачных ресурсов, а Ansible — за конфигурацию внутри ВМ.

Можно ли положить state на GitHub? Нет. Он может содержать чувствительные данные и технические детали. В командной эксплуатации используется защищённый удалённый backend с блокировкой.

Зачем lock-файл? Чтобы следующая установка использовала ту же версию провайдера, а не случайно обновлённую.

5. Разбор Terraform по шагам

yc iam create-token
$env:YC_TOKEN = yc iam create-token
terraform init
terraform fmt
terraform validate
terraform plan -var-file=../.private/vars.json -out=deploy.tfplan
terraform apply deploy.tfplan
terraform output -json

yc — CLI Яндекс Облака. iam create-token получает временный токен для API. Не публикуйте его вывод и не вставляйте токен в main.tf. В PowerShell запись в $env:YC_TOKEN устанавливает переменную только для текущего процесса и его потомков.

init скачивает провайдер — программу, которая переводит Terraform-ресурсы в вызовы API облака. В этом проекте основной реестр был недоступен, поэтому использовано зеркало Яндекс Облака. Это изменение способа доставки провайдера, а не замена самого облака.

fmt нормализует отступы. validate проверяет структуру конфигурации, но не гарантирует наличие квот или денег в облаке. plan вычисляет разницу между описанием и текущим состоянием. Сохранённый план позволяет применить именно рассмотренные действия. apply создаёт или меняет ресурсы; это команда с финансовыми последствиями. output -json возвращает адреса и идентификаторы для следующих этапов.

Ресурс yandex_compute_instance.vm использует for_each. Это означает: для каждой записи в словаре local.machines создать отдельную ВМ. Имя ключа — например, web-a — становится частью адреса ресурса в state. Если переименовать ключ, Terraform может увидеть удаление старого объекта и создание нового. Поэтому имена ключей не меняют без просмотра плана.

Ссылка yandex_vpc_subnet.lab[each.value.subnet].id задаёт зависимость. Terraform понимает: сначала создать подсеть, затем прикрепить к ней интерфейс. Не надо вручную расставлять паузы между созданием сети и ВМ.

Вопросы на защите

Чем plan отличается от apply? Plan показывает предполагаемые изменения; apply выполняет их.

Почему не выполнять apply сразу? Сначала нужно увидеть, не предлагает ли Terraform заменить диск или удалить ресурс, который должен сохраниться.

Что означает ~> в ограничении версии? Совместимый диапазон версий. Точный установленный выпуск закрепляется lock-файлом. Для строгого воспроизведения следите и за диапазоном, и за lock-файлом.

6. Разбор Ansible

Inventory группирует узлы по роли: [web], [elastic], [zabbix], [kibana], [bastion]. В строках стоят внутренние FQDN. На бастионе эти имена разрешаются через DNS облака. Параметр ansible_user=ubuntu задаёт пользователя SSH; become: true в playbook позволяет выполнять административные действия через sudo.

cd ~/diplom
ansible all -i ansible/inventory.ini -m ping
ansible-playbook -i ansible/inventory.ini ansible/site.yml --syntax-check
ansible-playbook -i ansible/inventory.ini ansible/site.yml
tail -n 40 ansible.log

-i выбирает inventory. Модуль ping в Ansible не посылает обычный ICMP echo: он проверяет SSH и возможность выполнить Python на удалённой машине. --syntax-check обнаружит ошибку YAML, но не проверит доступность Docker registry. Playbook выполняет задачи последовательно, а внутри каждой задачи обычно работает с несколькими машинами параллельно.

В отчёте ok означает, что желаемое состояние уже было достигнуто. changed — Ansible что-то изменил. failed — задача не выполнена. unreachable — к машине не удалось подключиться. Не называйте работу успешной, если в PLAY RECAP есть ненулевые failed или unreachable.

Большинство модулей Ansible идемпотентны: повторная задача apt не переустанавливает уже установленный пакет. В этой учебной версии задачи запуска контейнеров используют docker rm и docker run, поэтому повторный полный playbook перезапускает контейнеры. Данные БД сохранены в Docker volumes, но краткий перерыв возможен. В промышленной версии такие задачи следует заменить модулем управления контейнером или Compose с проверкой изменений.

Вопросы на защите

Что такое идемпотентность? Повторное применение желаемой конфигурации не должно само по себе создавать новые изменения. Здесь это верно для файлов и пакетов, но не полностью для shell-задач запуска контейнеров.

Почему no_log: true? Чтобы пароль БД не появился в stdout Ansible. Это не заменяет исключение файла секретов из Git.

Как исправлялась ошибка установки Zabbix agent? В образе Ubuntu отсутствовал пакет в доступных репозиториях; подключён официальный репозиторий Zabbix, затем установлен агент.

Проверь себя

  1. Кто создаёт ВМ? 2. Кто устанавливает nginx? 3. Зачем state? 4. Зачем lock-файл? 5. Что делает validate? 6. Что означает changed? 7. Почему Ansible ping не равен ICMP? 8. Что защищает no_log? 9. Чем опасен переименованный ключ for_each? 10. Можно ли запускать playbook повторно без последствий?
Ответы 1. Terraform. 2. Ansible. 3. Связывает код с объектами облака. 4. Фиксирует провайдер. 5. Проверяет конфигурацию, а не весь работоспособный стенд. 6. Состояние изменено. 7. Он проверяет SSH и Python. 8. Вывод задания, содержащий секрет. 9. Может вызвать замену ресурса. 10. Нужно понимать задачи: shell-команды этого проекта перезапускают контейнеры.

Часть 3. Сайт и доступность

7. Путь одного запроса

Пользователь вводит публичный адрес балансировщика. Браузер устанавливает TCP-соединение с портом 80 и отправляет HTTP-запрос GET /. Listener принимает его. HTTP router выбирает маршрут по пути. Virtual host связывает запрос с правилом маршрутизации. Backend group задаёт набор обслуживающих серверов. Target group содержит внутренние адреса двух nginx.

Эти объекты могут выглядеть избыточно для одной страницы, но каждый отвечает за свой уровень. Если позже появится /api, его можно направить в другую backend group, сохранив тот же внешний адрес и listener.

Healthcheck выполняется отдельно от пользовательского запроса. В этом проекте он обращается к / по HTTP на порт 80. Если подряд получены ошибки, балансировщик временно исключает сервер. Одна неудачная проверка и окончательная потеря сервера — разные события: пороги и интервал позволяют пережить кратковременный сбой.

Ключевая мысль. Балансировщик не исправляет сломанный nginx. Он только направляет запросы на оставшуюся исправную копию.

Вопросы на защите

Почему healthcheck именно на /? Это требование задания и минимальная проверка способности nginx отдать страницу. Для приложения проверка должна учитывать его реальные зависимости.

Почему у двух ВМ одинаковый HTML? Иначе при переключении пользователь получает разные версии сайта. Разные заголовки X-Backend используются только как диагностическая маркировка сервера.

Гарантируется ли строгое чередование серверов? Нет. Keep-alive, алгоритм балансировки и состояние backend могут влиять на выбор. Проверяется наличие обоих backend в выборке, а не схема «первый, второй, первый».

8. Разбор nginx

server {
    listen 80 default_server;
    root /var/www/html;
    add_header X-Backend $hostname always;
    location / { try_files $uri $uri/ =404; }
    location = /nginx_status {
        stub_status;
        allow 127.0.0.1;
        allow 10.42.1.20;
        deny all;
    }
}

listen 80 выбирает порт. default_server означает обработчик для запросов, не совпавших с более конкретным виртуальным сервером. root задаёт каталог файлов. try_files сначала ищет файл, затем каталог; если ни один не подходит, возвращает 404. Код 404 означает «не найдено» и не обязательно означает поломку всего nginx.

add_header X-Backend $hostname always добавляет в ответ имя ВМ. Оно помогает доказать, что трафик идёт на оба сервера. Параметр always сохраняет заголовок и в ответах с ошибкой. stub_status публикует техническую статистику nginx, поэтому доступ ограничен localhost и Zabbix server.

sudo nginx -t
sudo systemctl reload nginx
sudo systemctl status nginx --no-pager
curl -i http://127.0.0.1/
curl -s http://127.0.0.1/nginx_status

nginx -t проверяет конфигурацию без её применения. Если он успешен, reload перечитывает конфигурацию без обычного полного отключения процесса. status показывает состояние systemd-службы; --no-pager отключает интерактивный просмотрщик. curl -i выводит заголовки и тело. Для просмотра только заголовков можно использовать curl -I, но это HTTP HEAD, а не GET.

Вопросы на защите

Зачем проверять nginx -t до reload? Ошибка конфигурации должна быть обнаружена до применения.

Почему нельзя отдавать nginx_status всем? Это служебная статистика, необходимая мониторингу, а не посетителю сайта.

Где ошибка nginx? Сначала смотрите systemctl status, затем journalctl -u nginx и /var/log/nginx/error.log.

9. Как доказать отказоустойчивость

Правильная проверка имеет четыре шага: зафиксировать обычную работу, остановить nginx на одном сервере, проверить ответы балансировщика после исключения backend, вернуть nginx и доказать возвращение второй копии.

curl -v http://ALB_IP/
for i in $(seq 1 20); do curl -sD - -o /dev/null http://ALB_IP/ | grep -i X-Backend; done
sudo systemctl stop nginx
# На бастионе или клиенте повторить запросы к ALB.
sudo systemctl start nginx

Остановку выполняют только на одном web-узле. Первая серия покажет, какие серверы обслуживают сайт. После остановки нужен небольшой промежуток на healthcheck. Во время обнаружения возможны краткие ошибки: не скрывайте их и не обещайте нулевой перерыв без измерений. Итоговое подтверждение — успешные ответы оставшегося backend. После запуска nginx дождитесь двух успешных healthcheck и повторите выборку.

Нельзя назвать проверку выполненной, если вы проверили curl localhost на работающей ВМ. Это доказывает работу nginx, но ничего не говорит о маршруте через внешний балансировщик. Также нельзя одновременно остановить оба backend и ожидать доступный сайт.

Вопросы на защите

Какой отказ проверен? Отказ nginx на одной веб-ВМ. Это модель отказа одного backend, но не полная модель катастрофы всей облачной зоны.

Что остаётся единственной точкой отказа? Мониторинг и хранилище журналов в минимальной схеме. Для них потребовались бы дополнительные узлы и репликация.

Как избежать расхождения файлов? Разворачивать один и тот же site/index.html одним playbook на обе машины, затем сравнить sha256sum.

Проверь себя

  1. Что делает listener? 2. Где описан маршрут /? 3. Что содержит target group? 4. Зачем healthcheck? 5. Что означает 404? 6. Зачем X-Backend? 7. Чем reload отличается от stop/start? 8. Почему localhost недостаточно для проверки ALB? 9. Что сделать после остановки backend? 10. Что не доказывает успешная проверка отказа одного nginx?
Ответы 1. Принимает внешнее соединение. 2. В HTTP router/virtual host. 3. Адреса web-ВМ и подсети. 4. Исключает неисправный backend. 5. Ресурс не найден. 6. Маркирует обслуживший сервер. 7. Перечитывает конфигурацию без обычного полного остановa. 8. Не проверяется внешний путь. 9. Дождаться healthcheck и проверить ALB, затем восстановить nginx. 10. Полную устойчивость всех сервисов и всего облака.

Часть 4. Метрики и журналы

10. Что даёт мониторинг

Число «CPU 95%» отвечает на вопрос о нагрузке, но не объясняет, какой запрос вызвал проблему. Строка access.log показывает конкретный запрос, но не показывает запас памяти всей машины. Поэтому метрики и журналы дополняют друг друга.

Zabbix agent установлен на каждой ВМ. Сервер обращается к нему по TCP 10050, используя внутренний DNS. Ответ содержит значение конкретного item: загрузку CPU, использование памяти или пользовательский счётчик. В конфигурации также указан адрес активных проверок, но основные items этого проекта собираются в пассивном режиме. Не говорите, что все метрики «отправляются агентом самостоятельно»: направление зависит от типа item.

Термин Zabbix Смысл Пример
Host Наблюдаемый узел diplom-web-a
Item Одно измерение Процент использования диска
History Отдельные измерения Значения каждые 30 секунд
Trend Агрегат истории Среднее, минимум, максимум за час
Trigger Условие проблемы Диск больше 80%
Graph График значений CPU и пороговая линия
Dashboard Набор визуализаций USE по всем шести ВМ

Ключевая мысль. Зелёная страница входа в Zabbix не доказывает мониторинг. Доказательство — поддерживаемые items с обновляющимися lastvalue, история и работающие проверки.

Вопросы на защите

Почему Zabbix server в контейнере, а агент в ОС? Серверу нужны БД и веб-интерфейс; контейнеры упрощают установку. Агент в ОС читает ресурсы самой ВМ без путаницы с ограничениями контейнера.

Зачем PostgreSQL? Zabbix хранит там конфигурацию, историю измерений, события и пользователей. Потеря БД — потеря этих данных даже при работающем веб-контейнере.

Где посмотреть ошибки агента? journalctl -u zabbix-agent и /var/log/zabbix/zabbix_agentd.log.

11. USE на реальных ресурсах

USE расшифровывается как Utilization, Saturation, Errors: занятость ресурса, наличие очереди или давления и ошибки. Один высокий процент загрузки не всегда проблема. Если CPU занят полезной работой и очередь не растёт, машина может быть эффективно загружена. Если средняя загрузка по CPU невысока, но I/O очередь растёт, причина может быть в диске.

Ресурс Utilization Saturation Errors
CPU 100 минус idle Load average на ядро Аппаратные ошибки ядра, отдельно от нагрузки
RAM Использованная память % Swap %, allocation stalls Ошибки выделения и сигналы давления требуют дополнительной диагностики
Диск Использование корневой ФС % Незавершённые I/O в /proc/diskstats I/O errors в журнале ядра
Сеть Входящие/исходящие байты в секунду Dropped packets RX/TX errors
HTTP Запросы и соединения Активные соединения, длительность ответа 5xx и неуспешный HTTP-сценарий

Виртуальная машина не всегда предоставляет аппаратные счётчики физического CPU. Поэтому в книге нельзя обещать диагностику физического процессора по одной гостевой метрике. Нулевой счётчик kernel hardware errors означает «в доступном журнале таких сообщений не обнаружено», а не «железо гарантированно идеально».

Счётчики байтов и запросов накапливаются со временем. Чтобы получить скорость, Zabbix должен вычислить разницу между соседними измерениями и разделить её на время: preprocessing «Change per second». Без этого график с названием «байт/сек» на самом деле показывает сумму всех байтов с момента запуска — типичная ошибка начинающего администратора.

Пороговые линии не универсальны. CPU 80%, память 90%, диск 80% — учебные стартовые значения. Для CPU и RAM триггер использует усреднение за пять минут, чтобы одиночный всплеск не создавал лишний инцидент. При росте числа запросов пороги пересматривают с учётом запаса ёмкости.

cat /proc/loadavg
free -h
df -h /
cat /proc/net/dev
systemctl --failed --no-pager
sudo -u zabbix /usr/local/bin/diplom-metrics disk.queue

free -h показывает память в удобных единицах. Обращайте внимание на available: Linux использует свободную память для полезного кэша, поэтому маленькое free не всегда означает нехватку RAM. df -h / показывает заполнение файловой системы, а не нагрузку диска. Последняя команда запускает тот же коллектор от того же пользователя, что и агент. Это позволяет поймать проблему прав, которую запуск от root скрывает.

Вопросы на защите

Почему CPU 100% не обязательно авария? Важны очередь, длительность нагрузки и пользовательские симптомы.

Чем заполнение диска отличается от I/O queue? Первое показывает занятое место; второе — ожидающие или выполняющиеся операции ввода-вывода.

Почему появился unsupported item? Возможны неподдерживаемый ключ, отсутствие разрешений, неверный интерфейс или ошибка пользовательского скрипта. Проверяйте поле error и запускайте коллектор от пользователя zabbix.

12. Путь журналов

nginx записывает access.log и error.log. Filebeat читает их, хранит позицию чтения в своём registry и отправляет события в Elasticsearch по 9200. Elasticsearch индексирует документы. Kibana обращается к Elasticsearch и показывает их человеку. Kibana сама не является хранилищем журналов.

Docker volume Filebeat сохраняет registry после перезапуска контейнера. Без этого агент может повторно прочитать старые события. Volume Elasticsearch сохраняет индексы; удаление контейнера при сохранённом volume не должно удалять документы. Удаление volume — уже уничтожение данных.

sudo tail -n 10 /var/log/nginx/access.log
sudo tail -n 10 /var/log/nginx/error.log
sudo docker ps
sudo docker exec filebeat filebeat test output --strict.perms=false
curl -s http://diplom-elastic.ru-central1.internal:9200/_cluster/health
curl -s 'http://diplom-elastic.ru-central1.internal:9200/nginx-*/_count'

Команды curl к Elasticsearch выполняются внутри VPC. Внешнему посетителю порт 9200 не доступен. test output подтверждает соединение и совместимость с сервером, но не гарантирует успешную индексацию каждого события. Для этого проверяйте количество документов и журналы Filebeat.

Во время настройки возникла реальная ошибка схемы: поле service было строкой nginx, а стандарт ECS ожидает объект, например service.name. Elasticsearch возвращал 400 и отвергал события, хотя TCP-соединение работало. Исправление — передать service: {name: nginx}. Этот случай показывает, почему проверки «процесс запущен» недостаточно.

Вопросы на защите

Что такое индекс? Логическая группа документов с настройками поиска и схемой полей.

Что такое data view в Kibana? Представление, описывающее, какие индексы читать и какое поле использовать для времени.

Почему health Elasticsearch бывает yellow? В single-node схеме реплика shard не может размещаться на том же узле, что primary. Primary доступен, но реплика не назначена. Для учебного индекса replicas можно поставить 0; это не создаёт отказоустойчивость.

Часть 5. Эксплуатация и защита диплома

14. Резервная копия — не обещание, а путь восстановления

Диплом требует ежедневные snapshots дисков всех ВМ и хранение семь дней. Snapshot сохраняет состояние диска в облаке. Из него создаётся новый диск, который можно подключить к машине или использовать как загрузочный. Расписание задаётся cron-выражением 0 2 * * *: каждый день в 02:00 по времени планировщика облака, которое нужно сверить с его документацией; в отчёте используются UTC-метки.

Семь дней в Terraform выражены как retention_period = "168h". Это политика удаления снимков, созданных расписанием. Она не обязана удалять вручную созданные snapshots. Поэтому одноразовые тестовые копии нужно учитывать отдельно.

У снимка работающего диска есть ограничение: он обычно crash-consistent, то есть соответствует состоянию внезапного выключения. Файловая система и БД должны корректно восстановиться после такого состояния. Это не то же самое, что application-consistent резервная копия с завершённой транзакцией всех связанных компонентов. В производственной среде для БД добавляют собственный логический или физический backup и проверяют согласованность.

Ключевая мысль. Статус READY у snapshot доказывает создание копии. Только восстановление и проверка данных доказывают, что конкретный сценарий восстановления работает.

Вопросы на защите

Почему snapshot не заменяет репликацию сайта? Восстановление требует времени. Вторая nginx-копия обслуживает запросы сразу после исключения неисправного backend.

Какой RPO у ежедневного снимка? При успешном ежедневном выполнении можно потерять изменения после последнего снимка, приблизительно до суток. Фактическое окно зависит от времени сбоя и последнего успешного запуска.

Что такое RTO? Время восстановления сервиса после сбоя. Оно измеряется, а не выводится автоматически из расписания снимков.

15. Восстановление по шагам

yc compute snapshot-schedule list-snapshots SCHEDULE_ID
yc compute disk create --name diplom-restore-test --source-snapshot-id SNAPSHOT_ID --zone ru-central1-a
yc compute instance attach-disk diplom-web-a --disk-id RESTORE_DISK_ID
lsblk -f
sudo mkdir -p /mnt/restore-test
sudo mount -o ro,noload /dev/DEVICE_PARTITION /mnt/restore-test
sha256sum /var/www/html/index.html /mnt/restore-test/var/www/html/index.html
sudo umount /mnt/restore-test
yc compute instance detach-disk diplom-web-a --disk-id RESTORE_DISK_ID
yc compute disk delete RESTORE_DISK_ID

Это образец последовательности; конкретное устройство определяется по lsblk, а не угадывается. Новый диск может называться vdb или иначе. Монтирование ro означает чтение без намеренного изменения содержимого. Для ext4 после аварийного снимка могут потребоваться дополнительные параметры или отдельная проверка файловой системы; не запускайте ремонт поверх единственной копии.

Сравнение SHA-256 доказывает идентичность содержимого статического HTML-файла. Оно не доказывает корректность всей БД Zabbix и всех Elasticsearch индексов. В отчёте следует явно назвать, какие данные восстановлены и что проверено. После теста временный диск отсоединяют и удаляют, чтобы не расходовать бюджет.

Вопросы на защите

Почему новый диск создаётся из снимка? Snapshot не монтируется как обычная файловая система напрямую: из него сначала получается диск.

Почему mount только для чтения? Тест не должен изменять восстановленные данные без необходимости.

Что доказывает совпадение sha256sum? Что сравниваемые файлы имеют одинаковое содержимое, с практически достаточной для этой проверки уверенностью.

Порядок диагностики: сначала симптом пользователя, затем маршрут запроса, потом сервис и его зависимости. Вопросы на защите

Почему контейнер может быть Up, а приложение не работать? Процесс контейнера жив, но приложение ещё инициализируется, не подключено к БД или возвращает ошибку.

Как отличить RAM-проблему от заполнения диска? Проверить free, df, журнал ядра и exit-код контейнера. Код 137 часто связан с принудительным завершением, но причину подтверждают OOM-событием, а не угадывают.

Как действовать при неожиданном плане удаления? Не применять. Выяснить изменение ключей for_each, переменных, state или идентификаторов.

17. Сквозной практикум

Упражнение 1. Объясните маршрут

Нарисуйте путь «браузер → ALB → nginx → ответ». Назовите публичный и внутренний адрес на каждом участке. Хорошее решение объясняет, зачем нужен healthcheck. Ошибка новичка — показывать стрелку из интернета прямо к частному адресу web-a.

Упражнение 2. Проверьте идентичность сайта

На обеих web-ВМ выполните sha256sum /var/www/html/index.html. Хорошее решение сохраняет два вывода и один общий хеш. Ошибка новичка — сравнивать только имена файлов.

Упражнение 3. Проверьте отказ backend

Остановите nginx на одном узле, проверьте балансировщик, верните nginx. Хорошее решение фиксирует время и X-Backend, а также интервал исключения. Ошибка новичка — забыть восстановить сервис или назвать проверку localhost тестом ALB.

Упражнение 4. Найдите запрос в Kibana

Отправьте запрос с уникальным путём или User-Agent, затем найдите событие. Хорошее решение связывает запрос, время и поле node. Ошибка новичка — принять служебный Envoy healthcheck за собственный запрос.

Упражнение 5. Объясните график Zabbix

Покажите CPU, память, I/O queue и HTTP. Хорошее решение называет единицы и отличает счётчик от скорости. Ошибка новичка — назвать pused памяти процентом свободной памяти.

Упражнение 6. Восстановите файл

Создайте диск из snapshot, смонтируйте отдельно и сравните хеш HTML. Хорошее решение сохраняет snapshot-id, disk-id и вывод sha256sum. Ошибка новичка — заявить полное восстановление всех БД после проверки одного файла.

18. Как рассказать о дипломе

Начните с задачи: «Я построила отказоустойчивую инфраструктуру для статического сайта в Яндекс Облаке». Затем назовите ограничения: небольшой учебный бюджет, две зоны для сайта, отдельные ВМ для наблюдаемости, приватные веб-серверы и Elasticsearch. Объясните решение: Terraform создаёт ресурсы, Ansible на бастионе настраивает ОС и контейнеры.

После схемы переходите к доказательствам. Покажите запрос через ALB, X-Backend от обеих ВМ, результат остановки одного nginx, актуальные измерения в Zabbix, реальное событие nginx в Kibana и расписание снимков. Завершите ограничениями: минимальный стенд не обеспечивает кластеризацию Elasticsearch и БД мониторинга; HTTP не шифруется без сертификата, snapshot работающего диска не заменяет полноценный backup БД.

Плохой рассказ: «Я поставила Docker, всё работает». Хороший рассказ: «Пользователь входит через ALB, веб-серверы не имеют внешних IP. Я остановила nginx на одном узле, после healthcheck запросы продолжились на другой копии. Zabbix собирает метрики всех ВМ, Filebeat доставляет журналы обоих nginx, а восстановленный из снимка HTML совпал по хешу» — последнюю фразу произносите только после фактической проверки.

Короткие ответы для защиты

Какая часть отказоустойчива? Путь обслуживания статического сайта: две копии nginx в разных зонах и ALB.

Что защищает данные? Персистентные volumes и ежедневные снимки дисков с ограничением хранения. Для промышленной БД добавила бы application-consistent backup.

Что использовано для автоматизации? Terraform, yc CLI и Ansible; скрипт Zabbix API создаёт hosts, items, triggers и dashboards.

Почему контейнеры? Они упрощают доставку официальных версий сервисов и обходят проблемы скачивания Elastic-пакетов. Сами контейнеры размещены на облачных ВМ.

Как устроена безопасность? Минимальные входящие порты, закрытый Elasticsearch, SSH через bastion, ключевая аутентификация, секреты вне Git, пароли веб-интерфейсов.

Как проверить, что нет секретов в Git? Проверить gitignore, список staged файлов и поиск токенов. Не путать отсутствие .env в списке с гарантией: секрет мог оказаться в README или stdout.

Что улучшить дальше? TLS, закрытый доступ к панели через VPN, репликация БД мониторинга, кластер журналов, удалённый Terraform state, полноценные backup БД и автоматические проверки восстановления.
