# Часть 5. Эксплуатация и защита диплома

## 14. Резервная копия — не обещание, а путь восстановления

Диплом требует ежедневные snapshots дисков всех ВМ и хранение семь дней. Snapshot сохраняет состояние диска в облаке. Из него создаётся новый диск, который можно подключить к машине или использовать как загрузочный. Расписание задаётся cron-выражением `0 2 * * *`: каждый день в 02:00 по времени планировщика облака, которое нужно сверить с его документацией; в отчёте используются UTC-метки.

Семь дней в Terraform выражены как `retention_period = "168h"`. Это политика удаления снимков, созданных расписанием. Она не обязана удалять вручную созданные snapshots. Поэтому одноразовые тестовые копии нужно учитывать отдельно.

У снимка работающего диска есть ограничение: он обычно crash-consistent, то есть соответствует состоянию внезапного выключения. Файловая система и БД должны корректно восстановиться после такого состояния. Это не то же самое, что application-consistent резервная копия с завершённой транзакцией всех связанных компонентов. В производственной среде для БД добавляют собственный логический или физический backup и проверяют согласованность.

> **Ключевая мысль.** Статус READY у snapshot доказывает создание копии. Только восстановление и проверка данных доказывают, что конкретный сценарий восстановления работает.

### Вопросы на защите

**Почему snapshot не заменяет репликацию сайта?** Восстановление требует времени. Вторая nginx-копия обслуживает запросы сразу после исключения неисправного backend.

**Какой RPO у ежедневного снимка?** При успешном ежедневном выполнении можно потерять изменения после последнего снимка, приблизительно до суток. Фактическое окно зависит от времени сбоя и последнего успешного запуска.

**Что такое RTO?** Время восстановления сервиса после сбоя. Оно измеряется, а не выводится автоматически из расписания снимков.

## 15. Восстановление по шагам

```bash
yc compute snapshot-schedule list-snapshots SCHEDULE_ID
yc compute disk create --name diplom-restore-test --source-snapshot-id SNAPSHOT_ID --zone ru-central1-a
yc compute instance attach-disk diplom-web-a --disk-id RESTORE_DISK_ID
lsblk -f
sudo mkdir -p /mnt/restore-test
sudo mount -o ro,noload /dev/DEVICE_PARTITION /mnt/restore-test
sha256sum /var/www/html/index.html /mnt/restore-test/var/www/html/index.html
sudo umount /mnt/restore-test
yc compute instance detach-disk diplom-web-a --disk-id RESTORE_DISK_ID
yc compute disk delete RESTORE_DISK_ID
```

Это образец последовательности; конкретное устройство определяется по `lsblk`, а не угадывается. Новый диск может называться vdb или иначе. Монтирование `ro` означает чтение без намеренного изменения содержимого. Для ext4 после аварийного снимка могут потребоваться дополнительные параметры или отдельная проверка файловой системы; не запускайте ремонт поверх единственной копии.

Сравнение SHA-256 доказывает идентичность содержимого статического HTML-файла. Оно не доказывает корректность всей БД Zabbix и всех Elasticsearch индексов. В отчёте следует явно назвать, какие данные восстановлены и что проверено. После теста временный диск отсоединяют и удаляют, чтобы не расходовать бюджет.

### Вопросы на защите

**Почему новый диск создаётся из снимка?** Snapshot не монтируется как обычная файловая система напрямую: из него сначала получается диск.

**Почему mount только для чтения?** Тест не должен изменять восстановленные данные без необходимости.

**Что доказывает совпадение sha256sum?** Что сравниваемые файлы имеют одинаковое содержимое, с практически достаточной для этой проверки уверенностью.

## 16. Эксплуатационные команды

| Команда | Что выясняет | Где выполнять |
|---|---|---|
| `yc compute instance list` | Состояние ВМ | Рабочий компьютер с yc |
| `terraform plan` | Дрейф кода и облака | Каталог Terraform |
| `getent hosts ...` | DNS | Бастион или ВМ |
| `curl -v URL` | Соединение и HTTP | Клиент/бастион |
| `systemctl status nginx` | Состояние службы | Веб-ВМ |
| `journalctl -u nginx -n 50` | Ошибки запуска | Веб-ВМ |
| `docker ps -a` | Контейнеры и остановленные процессы | Нужная сервисная ВМ |
| `docker logs --tail 50 NAME` | Последние записи контейнера | Нужная сервисная ВМ |
| `df -h` | Свободное место | ВМ |
| `free -h` | RAM | ВМ |

Порядок диагностики: сначала симптом пользователя, затем маршрут запроса, потом сервис и его зависимости. Не перезапускайте все контейнеры одновременно «на всякий случай»: вы потеряете исходное состояние и можете создать второй сбой. Сначала сохраните журналы, потом выполните минимальное исправление и повторите ту же проверку.

### Вопросы на защите

**Почему контейнер может быть Up, а приложение не работать?** Процесс контейнера жив, но приложение ещё инициализируется, не подключено к БД или возвращает ошибку.

**Как отличить RAM-проблему от заполнения диска?** Проверить free, df, журнал ядра и exit-код контейнера. Код 137 часто связан с принудительным завершением, но причину подтверждают OOM-событием, а не угадывают.

**Как действовать при неожиданном плане удаления?** Не применять. Выяснить изменение ключей for_each, переменных, state или идентификаторов.

## 17. Сквозной практикум

### Упражнение 1. Объясните маршрут

Нарисуйте путь «браузер → ALB → nginx → ответ». Назовите публичный и внутренний адрес на каждом участке. Хорошее решение объясняет, зачем нужен healthcheck. Ошибка новичка — показывать стрелку из интернета прямо к частному адресу web-a.

### Упражнение 2. Проверьте идентичность сайта

На обеих web-ВМ выполните `sha256sum /var/www/html/index.html`. Хорошее решение сохраняет два вывода и один общий хеш. Ошибка новичка — сравнивать только имена файлов.

### Упражнение 3. Проверьте отказ backend

Остановите nginx на одном узле, проверьте балансировщик, верните nginx. Хорошее решение фиксирует время и X-Backend, а также интервал исключения. Ошибка новичка — забыть восстановить сервис или назвать проверку localhost тестом ALB.

### Упражнение 4. Найдите запрос в Kibana

Отправьте запрос с уникальным путём или User-Agent, затем найдите событие. Хорошее решение связывает запрос, время и поле node. Ошибка новичка — принять служебный Envoy healthcheck за собственный запрос.

### Упражнение 5. Объясните график Zabbix

Покажите CPU, память, I/O queue и HTTP. Хорошее решение называет единицы и отличает счётчик от скорости. Ошибка новичка — назвать pused памяти процентом свободной памяти.

### Упражнение 6. Восстановите файл

Создайте диск из snapshot, смонтируйте отдельно и сравните хеш HTML. Хорошее решение сохраняет snapshot-id, disk-id и вывод sha256sum. Ошибка новичка — заявить полное восстановление всех БД после проверки одного файла.

## 18. Как рассказать о дипломе

Начните с задачи: «Я построила отказоустойчивую инфраструктуру для статического сайта в Яндекс Облаке». Затем назовите ограничения: небольшой учебный бюджет, две зоны для сайта, отдельные ВМ для наблюдаемости, приватные веб-серверы и Elasticsearch. Объясните решение: Terraform создаёт ресурсы, Ansible на бастионе настраивает ОС и контейнеры.

После схемы переходите к доказательствам. Покажите запрос через ALB, X-Backend от обеих ВМ, результат остановки одного nginx, актуальные измерения в Zabbix, реальное событие nginx в Kibana и расписание снимков. Завершите ограничениями: минимальный стенд не обеспечивает кластеризацию Elasticsearch и БД мониторинга; HTTP не шифруется без сертификата, snapshot работающего диска не заменяет полноценный backup БД.

Плохой рассказ: «Я поставила Docker, всё работает». Хороший рассказ: «Пользователь входит через ALB, веб-серверы не имеют внешних IP. Я остановила nginx на одном узле, после healthcheck запросы продолжились на другой копии. Zabbix собирает метрики всех ВМ, Filebeat доставляет журналы обоих nginx, а восстановленный из снимка HTML совпал по хешу» — последнюю фразу произносите только после фактической проверки.

### Короткие ответы для защиты

**Какая часть отказоустойчива?** Путь обслуживания статического сайта: две копии nginx в разных зонах и ALB.

**Что защищает данные?** Персистентные volumes и ежедневные снимки дисков с ограничением хранения. Для промышленной БД добавила бы application-consistent backup.

**Что использовано для автоматизации?** Terraform, yc CLI и Ansible; скрипт Zabbix API создаёт hosts, items, triggers и dashboards.

**Почему контейнеры?** Они упрощают доставку официальных версий сервисов и обходят проблемы скачивания Elastic-пакетов. Сами контейнеры размещены на облачных ВМ.

**Как устроена безопасность?** Минимальные входящие порты, закрытый Elasticsearch, SSH через bastion, ключевая аутентификация, секреты вне Git, пароли веб-интерфейсов.

**Как проверить, что нет секретов в Git?** Проверить gitignore, список staged файлов и поиск токенов. Не путать отсутствие .env в списке с гарантией: секрет мог оказаться в README или stdout.

**Что улучшить дальше?** TLS, закрытый доступ к панели через VPN, репликация БД мониторинга, кластер журналов, удалённый Terraform state, полноценные backup БД и автоматические проверки восстановления.
